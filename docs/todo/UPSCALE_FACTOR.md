## Техническое задание (ТЗ) на реализацию варианта А: единый источник `upscale_factor`

### Цель
Устранить дублирование параметра `upscale_factor` в конфигурационных файлах, сделав единственным источником истины секцию `network_g` (которая определяет архитектуру модели). Датасет должен автоматически получать значение масштаба из этой секции, а параметр `datasets.train.upscale_factor` должен быть удалён из всех конфигов и из кода.

### Объем изменений

| Файл | Что менять |
|------|-------------|
| `libraries/training_dataset_nef.py` | Класс `CustomNEFPairDataset` – изменить способ получения `self.upscale_factor` |
| `run_training.py` | (опционально) Добавить проверку наличия ключа `network_g.upscale_factor` |
| Все конфигурационные YAML-файлы | Удалить строку `upscale_factor` из секции `datasets.train` (если она там есть) |

### Детали реализации

#### 1. Изменение в `training_dataset_nef.py`

**Текущий код (проблемный):**
```python
# в __init__
self.upscale_factor = opt.get('datasets', {}).get('train', {}).get('upscale_factor', 2)
```

**Новый код:**
```python
# в __init__
# Берём upscale_factor из секции network_g (архитектура модели)
# Если параметр не задан, используем значение по умолчанию 2
self.upscale_factor = opt.get('network_g', {}).get('upscale_factor', 2)
```

**Дополнительно:**  
Удалить из кода датасета любые упоминания `datasets.train.upscale_factor`.  
Оставить `assert` для проверки `gt_size == self.upscale_factor * lq_size` (он остаётся, но теперь использует единое значение).

#### 2. Проверка целостности (опционально, но рекомендуется)

В `run_training.py` после загрузки конфига добавить:

```python
if 'network_g' not in opt or 'upscale_factor' not in opt['network_g']:
    raise ValueError("Конфиг должен содержать network_g.upscale_factor")
```

Это гарантирует, что параметр присутствует.

#### 3. Обновление конфигурационных файлов

Из всех YAML-файлов (например, `RAW_NAFNet_Final_100.yml`, `RAW_NAFNet_Test_20_Final.yml`) удалить строку:

```yaml
datasets:
  train:
    upscale_factor: 4   # <-- эту строку удалить
```

При этом **оставить** `network_g.upscale_factor: 4`.

#### 4. Обратная совместимость

Если какой-то старый конфиг не содержит `network_g.upscale_factor`, код датасета использует значение по умолчанию `2`. Это безопасно, но желательно явно указать параметр во всех актуальных конфигах.

### Ожидаемый результат

- Единственное место, где задаётся масштаб восстановления – `network_g.upscale_factor`.
- Датасет автоматически использует это значение для вычисления координат кропа (`top_hq = top_lq * self.upscale_factor`).
- Исключена возможность рассинхронизации между моделью и датасетом.
- Упрощена настройка экспериментов: достаточно изменить `upscale_factor` в одном месте, и все компоненты (модель, датасет, валидатор) согласованы.

### Потенциальные риски и их mitigation

| Риск | Mitigation |
|------|-------------|
| Существующие конфиги без `network_g.upscale_factor` будут использовать значение по умолчанию 2 – может не совпадать с `downscale_factor` | Добавить в `run_training.py` предупреждение (лог), если `upscale_factor` не задан явно. |
| В будущем кто-то снова добавит `datasets.train.upscale_factor`, и оно будет проигнорировано | В документации (например, `UPDOWN_SCALE.md`) явно указать, что параметр устарел и не используется. При желании можно добавить проверку, которая выводит `DeprecationWarning`. |

### Критерии приемки

- [ ] При запуске `python run_training.py -opt config.yml` (с правильно настроенным `network_g.upscale_factor`) датасет загружается без ошибок.
- [ ] Размеры кропов HQ и LQ соответствуют масштабу (проверяется через `assert`).
- [ ] В конфиге отсутствует `datasets.train.upscale_factor`.
- [ ] Ни в одном месте кода (кроме документации) нет обращения к `datasets.train.upscale_factor`.

### Дополнительные рекомендации

- Синхронизировать `UPDOWN_SCALE.md` – указать, что `upscale_factor` задаётся только в `network_g`.
- В `CHANGES.md` добавить запись об удалении дублирования и переходе на единый источник.
