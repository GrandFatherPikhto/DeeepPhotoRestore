## 2. Главные системные противоречия (суть «сумбура»)

### 2.1 Несоответствие темы диссертации и реальной задачи

**В плане (главы 1–3)** указано:  
- Глава 1: анализ сенсоров с мозаичными светофильтрами (матрица Байера), методы демозаики.  
- Глава 2: пространственно-цветовая реставрация.  
- Глава 3: временная обработка видеопотока.  

**Что реально реализовано в коде и скриптах**:  
Устранение **JPEG-артефактов сжатия** на уже сформированных RGB-изображениях.  
При этом:  
- Нет обработки сырых RAW-данных (вы уже конвертируете RAW → RGB на этапе `download_and_convert.py`).  
- Нет демозаики (интерполяции байеровского паттерна).  
- Нет работы с видеопотоком.  
- Нет даже сравнения с классическими алгоритмами (AHD, VNG и пр.).

👉 **Вывод:** текущая реализация решает **частную задачу**, которая хотя и имеет отношение к качеству изображений, но **не соответствует заявленной теме диссертации**. Это критическое расхождение, которое нужно исправлять или переформулировать тему (с разрешения руководителя).

### 2.2 Датасет — проблема с «честным» RAW

Вы используете RAISE и конвертируете .NEF → RGB через `rawpy.postprocess()`. Это **уже скрытая демозаика** (выполненная библиотекой по умолчанию). Такой подход не позволяет исследовать методы обработки именно мозаичного сигнала. Для настоящего исследования сенсоров нужны:
- Либо оригинальные байеровские массивы (сырые данные без демозаики).
- Либо синтетическая генерация мозаичных изображений из полноцветных эталонов (алгоритм «Байеризация»).

### 2.3 Размер обучающей выборки

В документах фигурирует требование **4–5 тысяч фотографий**, но:
- Тестовый прогон сделан на 10 картинках (что нормально для отладки).
- Однако даже полный датасет RAISE (8k) — это **мало** для обучения глубокой сети с нуля или для качественного fine-tuning. Современные модели для реставрации обучаются на сотнях тысяч–миллионах примеров.

👉 Fine-tuning предобученной NAFNet на 5k картинках даст некоторый эффект, но **не позволит сделать научную новизну** (если только вы не вносите серьёзные изменения в архитектуру или постановку задачи).

### 2.4 Роль LLM (Llama) – формальное выполнение ТЗ

В одном из пунктов сказано: «реализовать алгоритм с помощью любой LLM на питоне». Вы интегрировали Llama через Ollama для генерации кода и отладки. Это **допустимо**, но в контексте диссертации выглядит как искусственная натяжка. Обычно LLM в таких проектах используют для автоматической разметки данных, генерации аугментаций, но не для замены исследовательского кода. Стоит либо убрать этот пункт (согласовав изменение ТЗ), либо показать более глубокое применение, например:
- LLM пишет варьируемые сценарии ухудшения изображений (разные типы шумов, артефактов).
- LLM помогает в анализе метрик и генерации выводов.

## 3. Технические замечания (мелкие, но важные)

### 3.1 Пути к датасету
В конфиге вы использовали абсолютные пути `/home/grand/Projects/...`. Это сделает проект немобильным. Лучше держать относительные и проверять наличие папок через `os.path.exists` или использовать переменные окружения.

### 3.2 Флаг `--no_cuda_ext` – правильно
Отключение компиляции кастомных CUDA-расширений оправдано на WSL (избегает проблем с компилятором). Потери производительности нет.

### 3.3 Качество JPEG-сжатия (quality=15)
Это очень сильное сжатие, артефакты будут чрезмерными. Для типичных исследований берут диапазон 10–30. Ваш выбор корректен, но стоит обосновать в диссертации.

### 3.4 Метрики (PSNR, SSIM) – только в конфиге
Вы их включили в логгер, но не показали, как собираете и анализируете. Для диссертации потребуется таблица сравнения с другими методами.
