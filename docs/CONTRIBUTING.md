# CONTRIBUTING.md – Руководство для разработчиков

Благодарим за интерес к проекту DeepPhotoRestore! Данный документ описывает правила и рекомендации по внесению изменений в код, оформлению коммитов, добавлению новых функций и тестированию. Соблюдение этих правил обеспечивает воспроизводимость результатов и упрощает совместную работу.

---

## 1. Как внести изменения

1. **Сообщите о намерении** – откройте Issue с описанием предлагаемого изменения (баг, новая фича, рефакторинг).
2. **Создайте ветку** от `main` (или `develop`):  
   `git checkout -b feature/краткое-описание`
3. **Внесите изменения**, следуя правилам оформления кода (см. раздел 2).
4. **Запустите проверки** (см. раздел 5).
5. **Создайте Pull Request** с описанием изменений и ссылкой на Issue.

---

## 2. Стиль кода

### 2.1. Python
- Следуйте [PEP 8](https://peps.python.org/pep-0008/).
- Используйте **4 пробела** для отступов (не табуляцию).
- Максимальная длина строки – **100 символов** (для комментариев – 72).
- Имена переменных и функций – `snake_case`. Классы – `CamelCase`.
- Константы – `UPPER_CASE`.

### 2.2. Импорты
- Порядок: стандартные библиотеки → сторонние → локальные модули.
- Избегайте `import *`.
- Используйте абсолютные импорты относительно корня проекта:  
  `from libraries.config import get_pipeline_config`.

```python
import os
import sys

import numpy as np
import torch

from libraries.logger import get_logger
from libraries.device import get_torch_device
```

### 2.3. Добавление новых модулей
- Новый функционал размещайте в `libraries/`.
- Название файла должно отражать суть: `new_feature.py`.
- Добавьте docstring в начало файла и в каждую публичную функцию/класс.
- Обновите документацию (`README.md`, `ARCHITECTURE.md` и др.), если новый модуль влияет на архитектуру.

### 2.4. Docstring
Используйте формат Google:

```python
def compute_psnr(pred, target):
    """Вычисляет PSNR между двумя изображениями.

    Args:
        pred (torch.Tensor): Предсказание, форма (B, C, H, W), диапазон [0,1].
        target (torch.Tensor): Эталон, форма (B, C, H, W), диапазон [0,1].

    Returns:
        float: Значение PSNR в децибелах.
    """
    ...
```

## 3. Коммиты и сообщения

- Пишите сообщения на **русском** или **английском** (единообразие внутри проекта).
- Формат:  
  `[Тип] Краткое описание (не более 50 символов)`
- Типы:
  - `[Fix]` – исправление ошибки.
  - `[Feature]` – новая функциональность.
  - `[Refactor]` – рефакторинг без изменения функционала.
  - `[Docs]` – обновление документации.
  - `[Config]` – изменение конфигурационных файлов.
  - `[Test]` – добавление или правка тестов.

Пример:
```
[Fix] Исправлен вызов log_validation_metrics в run_training.py
```

---

## 4. Добавление новых метрик или лоссов

Если вы хотите добавить новую метрику в логи или новый лосс:

1. Создайте класс/функцию в соответствующем модуле (`training_losses.py`, `training_utils.py`).
2. Добавьте параметры в YAML‑конфиг (если нужно).
3. Обработайте новый параметр в `config.py` (если требуется).
4. Внедрите вызов в `run_training.py` или `training_logger.py`.
5. Обновите документацию (`CONFIG.md`, `TRAINING.md`).

**Важно:** Не нарушайте обратную совместимость со старыми конфигами. Если меняете интерфейс, предусмотрите значения по умолчанию.

## 5. Тестирование

Хотя в проекте нет автоматических тестов (на данный момент), перед отправкой PR выполните ручную проверку:

### 5.1. Smoke‑тест (предобученческий)
```bash
python run_pipeline.py -opt configs/your_config.yml
```
Ожидаемый вывод: `🎉 ВСЕ ПРОВЕРКИ ПРОЙДЕНЫ УСПЕШНО!`

### 5.2. Обучение на малом датасете
- Создайте временный конфиг с `num_epochs=2`, `validation_freq=1`, `log_csv=true`.
- Запустите обучение и убедитесь, что:
  - Файлы `train_metrics.csv` и `val_metrics.csv` создаются.
  - Потери не становятся `NaN`.
  - Модель сохраняет чекпоинт.

### 5.3. Визуальная проверка
- После 2 эпох проверьте `experiments/{name}/val_predictions/` – изображения не должны быть чёрными или артефактными.

### 5.4. Проверка геометрии
```bash
python -c "
from libraries.training_dataset_nef import CustomNEFPairDataset
from libraries.config import get_pipeline_config
opt = get_pipeline_config()
ds = CustomNEFPairDataset(
    opt['path']['dataset_root'] + '/train/lq_inputs',
    opt['path']['dataset_root'] + '/train/hq_targets',
    opt=opt
)
lq, hq = ds[0]
assert lq.shape[1]*opt['network_g']['upscale_factor'] == hq.shape[1]
print('OK')
"
```

## 6. Обновление документации

При любом изменении, влияющем на пользователя или разработчика, необходимо обновить соответствующие файлы:

- `README.md` – общая информация, быстрый старт.
- `ARCHITECTURE.md` – если меняется структура модулей или потоки данных.
- `ALGORITHM.md` – если меняются алгоритмы (например, деградация, лосс).
- `CONFIG.md` – если добавляются/удаляются/меняются параметры YAML.
- `PIPELINE.md` – если меняются скрипты запуска.
- `TRAINING.md` – если меняются гиперпараметры, стратегия обучения.
- `PLOT.md` – если меняются форматы CSV или доступные графики.
- `UPDOWN_SCALE.md` – если меняется логика масштабирования.
- `CHANGES.md` – добавляйте запись о любом значимом изменении.

## 7. Воспроизводимость

- **Фиксируйте seed** в конфиге (параметр `manual_seed`).
- **Не используйте случайные операции без фиксации** (например, `random.random()` лучше заменить на `np.random` с фиксированным seed).
- При добавлении новых аугментаций убедитесь, что они **синхронны для LQ и HQ** и **не нарушают топологию RGGB**.
- Избегайте глобальных состояний, которые могут влиять на порядок вычислений.

---

## 8. Работа с чекпоинтами

- Не изменяйте архитектуру модели без необходимости – чекпоинты станут несовместимы.
- Если изменение архитектуры неизбежно, предусмотрите скрипт конвертации чекпоинта (можно добавить в `tools/convert_checkpoint.py`).
- При создании новой обёртки сохраняйте совместимость со старыми весами через `strict=False` и фильтрацию.
